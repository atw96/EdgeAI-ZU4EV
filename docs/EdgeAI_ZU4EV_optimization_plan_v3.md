## 0. 结论

1. **B1 失败是预期内的结果，Q8 线永久关闭，保留 Q6。** 测试集上 Q6=81.95%、Q8=82.29%，而任务书里的学生 FP32 测试集是 81.05% [反馈]。Q6 在测试集上并不比 FP32 差，v1/v2 里「Q6 比 FP32 低 1～2 点」来自验证集（79.17% vs 81.19%），不适用于测试集。**位宽不是精度瓶颈，容量才是。**
2. **B2（加宽）不应被 B1 的准入卡住。** 两者独立。v2 §8 把 B2 的前置条件定为「板端延迟 ≤2 ms」，现在 B2 卡的是**每个乘法器的面积代价没搞清楚**，不是精度。
3. **A1' 的 csynth 结果推翻了 v2 的两个判断：**
   - conv1a 单层 1.318 ms = 263 600 拍 = **257 拍/输出像素 ≈ 9.5×RF**（RF=27）。模型预期 27 648 拍。**这一层走的是 `rf_leq_nin`，没有 IndexLoop，仍然慢 9.5 倍，所以 H1（IndexLoop）不能解释 conv1a。**
   - 顶层延迟 265 445 拍≈conv1a 一层，说明至少 conv1b（模型 147 456 拍）不是 9.5×，也说明 **csynth 里 dataflow 是重叠的（H2 在 csynth 里被否定）**。所以「全层统一 ×9 且串行」的说法不成立；v2 §0 第 3 条把它当成两个结构性问题同时存在，说重了。
   - 因此现在有**两个独立的未解释项**：conv1a 的 9.5×，以及基线板端 57.43 ms 与周期模型的差距（基线是否有 IndexLoop 问题仍未验证）。
4. **A1' 不是「小步」，而是 `RF≤n_in` 这个家族的最小点。** 该家族里 P ≥ n_out，ΣP 下限 = Σn_out = 120 [源码+计算]。再往下只能走 `RF>n_in` 分支（带 IndexLoop）。所以「RF≤n_in 会爆面积」与「RF>n_in 会慢 9 倍」是夹住你的两堵墙，**能否通过补丁修好 IndexLoop 决定了面积高效区能不能用。**
5. **面积 96 141 LUT / 278 BRAM / 243 DSP 不能用乘法器数线性解释。** 基线 ΣP=24 实现后 24.7k LUT / 26 BRAM / 39 DSP，A1' ΣP=120 的 csynth 是 3.9× LUT、10.7× BRAM、6.2× DSP。+96 个乘法器带来 +252 个 BRAM_18K，权重本身（共 18 720×6 bit）装不下这么多，所以**面积主要来自别处**（候选：FIFO 深度、line buffer、宽权重字、n_in:1 数据选择器）。归因要看 csynth 的逐实例表，不要猜。
6. **csim 与 Keras 的 MAE 0.088（对比 v1 门禁 0.026）是流水线可复现性问题，不是 RF 问题。** 重新转换改写了卷积核和 BN 头文件，说明当前转换路径与部署 bit 的导出不是同一套。10 张图上 9/10 对 10/10 没有统计意义。必须先把这件事做成受控实验，否则后面所有结果都无法归因。
7. **csynth 延迟 ≠ 板端延迟。** 基线的 csynth 还没重跑过。你们历史上有过 csynth 13.37 ms 对板端 57 ms（v1 称非同一个 bit）。在没有基线 (csynth, 板端) 配对点之前，A1' 的 1.33 ms 可能对应板端几 ms，而不是 1.7 ms。

| v2 的说法 | 现状 |
|---|---|
| B1 预期能追回「Q6 相对 FP32 的 1～2 点」 | 前提错（来自验证集）。测试集上 Q6 已不低于 FP32 |

## 2. 新的优先级（每步只读或仅 csynth，按顺序）

### P1. 受控数值对比：RF 作为唯一变量

目的：分开「RF 的影响」与「重新转换带来的导出漂移」。

1. 同一个 conda 环境、同一个 h5、同一个脚本提交，**先后各转换一次**：(a) 基线 `RF_PER_LAYER`（P=4）；(b) A1'。
2. `diff -r` 两个工程的 `firmware/weights/*.h` 与 `defines.h`：**除 RF 相关参数外必须逐字相同**。若权重头文件不同，说明转换本身不确定，那是 bug，先停下。
3. 再把 (a) 的头文件与「产出当前已部署 bit 的那次导出」对比（若没归档，就是你说的转换前那次 10 样本 P4 csim 的工程目录）。找出漂移来源：hls4ml 版本、QKeras 版本、`bit_exact` 流程、h5 来源（`model_int8_qkeras.h5` vs v19 微调导出）、BN 融合。
4. csim 用**测试集前 1000 张**，不要用 100 张 bench（你们已经在 1 万张上跑 Keras，数据是有的）。报告：(a) 与 (b) 的 GAP 输出是否逐比特一致；二者各自与 Keras GAP 的 MAE/最大值；Top-1 与 Keras 的 81.95% 比较。
5. 门：(a)=(b) 逐比特一致；MAE 回到 ≤0.05 量级（部署 bit 当时是 0.026）；Top-1 与 Keras 差 ≤1 点。**不过门不进入 P2 之后的任何综合。**

### P2. 零成本归因（用已有的 A1' csynth 报告，不跑新综合）

从 A1' 的 csynth 报告提取并存入 `results/opt_v2/p2_attribution.json`：

- **逐实例表**：zeropad、conv1a…conv3b、各 relu、pool、gap 的 Latency、Interval、LUT、FF、DSP、BRAM_18K。回答：96k LUT 与 278 BRAM 各自属于谁。
- **conv1a 的循环表**：`ReadInputHeight`/`ReadInputWidth` 的 trip count 与 iteration latency；被内联的 `ReuseLoop`（以及是否出现 `IndexLoop`）的 trip count、Iteration Latency、**achieved II**。
- 日志里的关键词：`Final II`、`Pipelining result`、`Unable to`、`dependence`、`carried`。目标是确认 257 拍/像素是 `27×9.5`（ReuseLoop II≈9.5）还是别的结构。
- FIFO：每条 stream 的深度与实现（BRAM/LUTRAM/SRL）。

产出结论只有三种：(i) conv1a 的 ReuseLoop II>1，有明确原因；(ii) 慢在像素循环的非流水化路径；(iii) 别的。**三种对应的后续动作不同，不要在此之前改 RF。**

### P2b. 基线重跑 csynth，建立 csynth→板端的对应关系

用当前工具链对**基线 P=4** 配置跑一次 csynth（与 P1 的 (a) 同一个工程），记录每层与顶层延迟、资源。用它和板端 57.43 ms 配对得到比值 `r = 板端/csynth`。之后所有 csynth 结果用 `r` 换算预期板端延迟（`r` 是否稳定，用第二个已知点验证）。

### P3. 用真实面积代替 csynth 估计

对 A1' 工程执行（Vivado HLS 2020.1）：

```tcl
export_design -rtl verilog -format ip_catalog -flow syn     # 只综合，IP 单独，约十几到二十几分钟
# 需要布局布线时间时再用 -flow impl
```

读 `report_utilization`。HLS 的 LUT 估计往往偏保守，BRAM/DSP 的估计通常较准；**BRAM 278 超过 256 这一项大概率是真的，LUT 的 109.5% 需要用综合结果核实**。同时核对 URAM 行（器件目录写 XCZU4EV 有 48 个 UltraRAM，你的 HLS 报告写 0）。

### P4. 单层微基准（stock hls4ml，不带你们的补丁）

目的：判断 conv1a 的异常来自 stock hls4ml + 工具版本，还是你们的补丁流程。四个单层 Keras 模型，io_stream、Resource、`xczu4ev-sfvc784-1-i`、5 ns、只跑 csynth：

| 模型 | RF 取值 |
|---|---|
| Input 32×32×3 → Conv2D(16,3,same) | 27 与 108 |
| Input 32×32×16 → Conv2D(16,3,same) | 144 与 576 |

读每个的循环表（achieved II、迭代延迟）与总延迟，对照 `px×RF`。再把同样的两层放进你们的补丁流程重做一次。三种可能的结论：stock 就慢（工具/代码本身）、只有补丁流程慢（补丁引入）、都不慢（问题在整网上下文，如上游的 zeropad / input_qact 流）。

### P5. IndexLoop 补丁实验（直接检验 H1 对基线的作用）

只在 P1 过门之后做。

- 本地补丁 `nnet_dense_resource.h::dense_resource_rf_gt_nin_rem0`：给 `IndexLoop` 加 `#pragma HLS PIPELINE II=1`，或把 `outidx` 改成编译期可折叠的查表。补丁进入你们现有的 patch 列表并留档，源码处写根因注释。
- **对基线 P=4 配置**重跑 csynth。预期：
  - 若 H1 对基线成立：各层周期显著下降，顶层趋近 conv1b 的 589 824 拍（2.95 ms），**面积几乎不变**。这一点单独就是一个有价值的结果：按 P2b 的 `r` 换算，若 `r` 近似为 1，则板端约 3.4 ms，比 CPU 的 12.23 ms 快约 3.6×，面积还是基线的 28% LUT。
  - 若顶层几乎没变：H1 对基线也不成立，删掉这条线，回到 P2/P4 的结论。
- 门：GAP 输出与未打补丁版本逐比特一致。

### P6. FIFO 深度优化与 ReLU 合并（从 v2 的「最后」提前）

BRAM 278>256 是硬阻塞，FIFO 是最常见的 BRAM 大户。按 hls4ml 文档「FIFO Buffer Depth Optimization」页的流程做（需 RTL cosim 采集各 stream 的最大占用），并检查是否有可用的 ReLU 合并 pass。MLPerf Tiny 论文里这两项使一个 hls4ml CIFAR-10 模型的 HLS 估计 BRAM 从 477 降到 146，**网络不同，不要外推，只当方向参考**。P2 的逐实例表会告诉你 FIFO 占了多少，占比小就别花时间。

## 3. 面积-延迟前沿（P5 通过或补丁后才可用）

`python3 rf_planner.py --frontier` 的结果（只是乘法器数 ΣP 与理想周期，**不是面积**；面积要用 P2/P3 的实测拟合）：

| 最大层周期 | 理想值(200 MHz) | ΣP | 每层 RF（conv1a/1b/2a/2b/3a/3b）| 需要补丁？ |
|---:|---:|---:|---|---|
| 589 824 | 2.95 ms | 11 | 432 / 576 / 1440 / 1800 / 4320 / 5184 | 是 |
| 300 000 | 1.50 ms | 21 | 216 / 288 / 720 / 900 / 4320 / 2592 | 是 |
| 200 000 | 1.00 ms | 33 | 108 / 144 / 720 / 720 / 2160 / 2592 | 是 |
| 150 000 | 0.75 ms | 40 | 108 / 144 / 576 / 360 / 2160 / 1728 | 是 |
| 100 000 | 0.50 ms | 67 | 54 / 72 / 288 / 360 / 1440 / 1296 | 是 |
| 60 000 | 0.30 ms | 108 | 54 / 48 / 144 / 180 / 720 / 864 | 是 |
| 36 864 | 0.18 ms | 160 | 27 / 36 / 144 / 90 / 540 / 432 | 部分 |
| `RF≤n_in` 家族下限（A1'）| 0.74 ms | **120** | 27 / 144 / 144 / 180 / 180 / 216 | 否 |

读法：在**不打补丁**的世界里只有两个点：基线（ΣP=24，慢）和 A1'（ΣP≥120，面积大）。**打补丁之后才出现 ΣP=33～67 的中间区**，同样的延迟只需要 A1' 一半甚至三分之一的乘法器。

## 4. 重新设定的目标（分级，替代 v2 的「A2 三档」）

| 级别 | 目标 | 达成路径 |
|---|---|---|
| T0 | 弄清 conv1a 的 9.5× 与基线 57 ms 的来源 | P1、P2、P2b、P4 |
| T1 | 板端 ≤3.5 ms，面积不高于基线 | P5 成功即达成 |
| T2 | 板端 ≤1.5 ms，LUT<60k，BRAM<70% | 在 T1 之上按第 3 节前沿逐点提高 P，每点实测 |
| T3 | 板端 ≤0.7 ms（stretch） | 需要 conv1a 异常被消除，且面积归因后有余量 |

CPU TFLite 是 12.23 ms。T1 已经比 CPU 快 3.6×，对作品集有意义；不必一上来追 0.74 ms。

推进规则沿用 v2 §5.4 的前三条（一次一档；停手条件；红线 LUT<60k / DSP<500 / BRAM_18K<160 / WNS≥0），**第 2 条的「线性外推」换成：每做完一档，用逐实例表更新「每个乘法器带来的 LUT/BRAM/DSP」，再预测下一档。**

## 5. 精度线（修订）

| 编号 | 内容 | 状态 / 条件 |
|---|---|---|
| B1 | Q6→Q8 | **关闭**。+0.34 点，p=0.130，且位宽增加会让面积更差 |
| B0（新） | **固定架构（16/16/20/20/24/24）的纯训练改进**：先在同一个固定 1 万张上重测 FP32 与 Q6（确认 Q6≥FP32），再尝试更强的老师、KD 的 α/T 重扫、数据增强、更长的训练 | 无需改 RTL，但权重变了就要重新转换/综合，所以放在硬件路径稳定之后，与下一次硬件改动合并。判据同 B1：10 000 张配对检验 p<0.05 且净增 ≥1 点 |
| B2 | 加宽 | **与 B1 脱钩**。前置条件改为：P2/P3 已得到「每乘法器面积」的实测数，且 T1 已达成。候选先做中间档 **24/28/32**（MAC 10.43 M≈2.06×），再看 32/40/48（19.39 M≈3.83×）。每个候选先用 `rf_planner.py --widen` 算合法 RF，再按实测面积判断装不装得下 |

B0 预期收益只是量级猜测：同架构下容量是上限，不要承诺数字。

## 7. 约束（沿用并补充）

1. 一次只改一件事；每步先写预测再运行。
2. 转换、csynth、板端三类结果每次都带 bit/hwh MD5 与脚本 commit，写进 `results/opt_v2/*.json`，不覆盖旧文件。
3. 不再用 100 张 bench 下任何数值结论；csim 至少 1000 张，板端精度用 1 万张。
4. 已部署 bit 与 Q6 权重不覆盖，继续保持。
5. 每个源码改动就地写根因注释。
