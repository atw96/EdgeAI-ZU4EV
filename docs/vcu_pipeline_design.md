**Platform**: ALINX ACU4EV (XCZU4EV-1SFVC784I)  
**Status**: Concept Design / Roadmap  
**Tool versions**: Vivado 2020.1 · PetaLinux 2020.1 · Vitis Video SDK 2020.1

## 1. System Overview

The base EdgeAI-ZU4EV project demonstrates still-image CIFAR-10 inference.
This document describes the architectural extension that feeds **live H.264/H.265
video** from a USB camera or RTSP stream through the on-chip **VCU (Video Codec
Unit)** hardware decoder, pipes decoded frames to the **PL-side HLS CNN
accelerator**, and returns annotated video with classification labels overlaid
via an **OSD (On-Screen Display)** module — all at real-time frame rates.

```
┌────────────────────────────────────────────────────────────────────────┐
│                     Full VCU Inference Pipeline                        │
│                                                                        │
│  [Camera / File]                                                       │
│       │ H.264/H.265 bitstream                                          │
│       ▼                                                                │
│  ┌─────────────┐     ┌─────────────────────────────────────────────┐  │
│  │  PS: GStreamer│     │          Programmable Logic (PL)           │  │
│  │  Pipeline    │     │                                             │  │
│  │             ├────►│ ┌──────────┐  AXI-S  ┌──────────────────┐  │  │
│  │  VCU Decoder│     │ │YUV→RGB   ├────────►│ HLS CNN Accel    │  │  │
```

## 2. Data Flow Design

### 2.1 Stage 1 — Video Ingestion & H.264 Decode (VCU)

The XCZU4EV VCU is a **dedicated hardware block** supporting:
- H.264 (AVC) decode up to 4K @ 30 fps
- H.265 (HEVC) decode up to 4K @ 60 fps
- YUV 4:2:0 output format

On PetaLinux 2020.1, the VCU is accessed via the **al5d** kernel driver
and exposed through GStreamer's `vcu_dec` element:

```bash
# GStreamer pipeline: USB camera → H.264 encode → VCU decode → YUV frames
gst-launch-1.0 \
  v4l2src device=/dev/video0 ! \
  video/x-raw,width=1920,height=1080,framerate=30/1 ! \
  omxh264enc ! h264parse ! \
  vcu_dec ! \
  video/x-raw,format=NV12 ! \
  appsink name=sink
```

The VCU outputs frames in **NV12** format (YUV 4:2:0 semi-planar):
- Y plane: 1920 × 1080 = 2,073,600 bytes
- UV plane: 1920 × 540 = 1,036,800 bytes interleaved
- **Total per frame**: 3,110,400 bytes @ 30 fps = **93.3 MB/s**

### 2.2 Stage 2 — YUV → RGB Colour Space Conversion (PL HLS)

The CNN accelerator expects RGB input (32×32×3). A lightweight HLS IP
performs two operations:

**2.2.1 YUV→RGB BT.601 conversion**:

```
R = Y + 1.402  × (V - 128)
G = Y - 0.344  × (U - 128) - 0.714 × (V - 128)
B = Y + 1.772  × (U - 128)
```

Implemented in HLS with `ap_fixed<10,8>` arithmetic (avoids floating point,
maps efficiently to DSP48E2 multipliers).

**2.2.2 Region-of-Interest resize → 32×32**:

A simple **nearest-neighbour downscaler** crops a configurable ROI from the
full-resolution frame and downscales to 32×32. For production, bilinear
interpolation (also implementable in HLS) improves accuracy.

```cpp
// HLS pseudocode for YUV→RGB + resize IP
void yuv_to_rgb_resize(
    hls::stream<ap_axiu<8,0,0,0>> &yuv_in,   // NV12 stream
    hls::stream<ap_axiu<8,0,0,0>> &rgb_out,  // RGB 32x32 stream
    ap_uint<12> roi_x, ap_uint<12> roi_y,    // ROI top-left
    ap_uint<12> roi_w, ap_uint<12> roi_h     // ROI size
) {
    #pragma HLS INTERFACE axis port=yuv_in
    #pragma HLS INTERFACE axis port=rgb_out
    #pragma HLS INTERFACE s_axilite port=roi_x
    // ... conversion logic
}
```

### 2.3 Stage 3 — CNN Inference (Existing HLS Accelerator)

The `cifar10_accel` IP (generated by hls4ml Phase 1C) receives the 32×32×3
RGB stream and outputs 10-class softmax scores. No modification is required
to the accelerator itself — only the upstream YUV→RGB IP is new.

### 2.4 Stage 4 — OSD Annotation (PS GStreamer)

Classification results are passed back to the PS via the existing DMA S2MM
channel. A GStreamer `textoverlay` element stamps the label and confidence
score onto each frame before output:

```bash
# Conceptual output pipeline with OSD
... | textoverlay text="" font-desc="Sans 24" ! \
    fpsdisplaysink video-sink=autovideosink
```

The Python control loop reads DMA results and dynamically updates the
`textoverlay` property via GObject/GStreamer Python bindings.

## 3. Key Technical Challenges & Solutions

### 3.1 Frame Buffer Management

**Challenge**: The VCU outputs full-resolution frames (3.1 MB each). The CNN
only needs a 32×32 crop. Copying the entire frame to PL is wasteful.

**Solution**: Use a **zero-copy ROI DMA** approach:
- VCU writes frame to PS DDR via its internal DMA
- The YUV→RGB HLS IP reads only the ROI region directly from DDR via an
  AXI4 Master interface (address computed from ROI parameters)
- Only 32×32×2 bytes (NV12 ROI) cross the PS-PL AXI bus

### 3.2 Clock Domain Management

| Domain | Clock | Used by |
|--------|-------|---------|
| VCU decode | 667 MHz (internal) | VCU hardware |
| PS ARM | 1333 MHz | GStreamer, Python |
| PL inference | 200 MHz (pl_clk0) | HLS CNN accel, YUV→RGB IP |
| PL DDR ctrl | 100 MHz (pl_clk1) | DMA control |

The YUV→RGB IP and CNN accelerator share the 200 MHz domain. AXI4-Stream
handshaking handles back-pressure automatically.

### 3.3 Timing Synchronisation

Frames arrive from VCU at 30 fps (33.3 ms period). CNN inference must
complete within this window. For CIFAR-10 at 200 MHz with ~2 ms HLS latency,
**16× headroom** is available — allowing processing of multiple ROIs per frame
(e.g., sliding-window object detection).

If inference latency exceeds one frame period, a **double-buffer** scheme
is needed:
- Buffer A: VCU decoding frame N+1
- Buffer B: HLS IP processing frame N

This is implementable using two pre-allocated PYNQ `allocate()` buffers.

## 4. Bandwidth Budget Analysis

### 4.1 PL DDR4 (1 GB, 16-bit @ 2400 MT/s)

```
Theoretical peak bandwidth:
  16-bit bus × 2400 MT/s = 38.4 Gb/s = 4.8 GB/s

VCU frame write to PS DDR (via PS HP port):
  1080p30 NV12 = 3.11 MB × 30 fps = 93.3 MB/s   → PS DDR4 (4 GB)

ROI read by YUV→RGB HLS IP (32×32 @ 30 fps, NV12):
  32 × 32 × 1.5 bytes × 30 fps = 46,080 bytes/s  → negligible

CNN result write (10 × 4 bytes @ 30 fps):
  1,200 bytes/s                                   → negligible

Total PL-side DDR4 read bandwidth:
  ~46 KB/s (well within 4.8 GB/s limit)
```

**Conclusion**: The PL DDR4 bandwidth is **not a bottleneck** for this pipeline.
The primary bandwidth concern is the PS DDR4 for VCU frame buffering, which at
93 MB/s is well within the PS DDR4's ~25 GB/s theoretical bandwidth.

### 4.2 AXI4-Stream Throughput (200 MHz, 8-bit TDATA)

```
ROI pixel throughput needed:
  32 × 32 × 3 channels × 30 fps = 92,160 bytes/s

AXI-Stream capacity @ 200 MHz, 8-bit:
  200 × 10^6 bytes/s = 200 MB/s

Utilisation: 0.046%   → no throughput constraint
```

## 6. GStreamer + PYNQ Integration Code Sketch

```python
import gi
gi.require_version('Gst', '1.0')
from gi.repository import Gst, GLib
from pynq import Overlay, allocate
import numpy as np
import threading

Gst.init(None)

overlay    = Overlay('cifar10_accel.bit')
dma        = overlay.axi_dma_0
in_buf     = allocate(shape=(32*32*3,), dtype=np.uint8)
out_buf    = allocate(shape=(10,),      dtype=np.float32)

CLASS_NAMES = ['airplane','automobile','bird','cat','deer',
               'dog','frog','horse','ship','truck']

latest_label = 'initialising...'

def on_new_sample(sink):
    """Called by GStreamer appsink for each decoded frame."""
    global latest_label
    sample = sink.emit('pull-sample')
    buf    = sample.get_buffer()

    # Map buffer to numpy (NV12 frame)
    ok, mapinfo = buf.map(Gst.MapFlags.READ)
    nv12_data   = np.frombuffer(mapinfo.data, dtype=np.uint8)
    buf.unmap(mapinfo)

    # Extract centre 32×32 ROI from Y plane (luminance only for demo)
    # Full YUV→RGB would use the PL HLS IP via AXI-Lite ROI registers
    H, W = 1080, 1920
    y0   = (H - 32) // 2
    x0   = (W - 32) // 2
    y_plane = nv12_data[:H*W].reshape(H, W)
    roi_y   = y_plane[y0:y0+32, x0:x0+32]

    # Replicate Y to RGB channels (greyscale fallback; replace with PL HLS)
    rgb_roi = np.stack([roi_y, roi_y, roi_y], axis=-1).flatten()
    np.copyto(in_buf, rgb_roi)

    # Run FPGA inference
    dma.sendchannel.transfer(in_buf)
    dma.recvchannel.transfer(out_buf)
    dma.sendchannel.wait()
    dma.recvchannel.wait()

    pred         = np.argmax(out_buf)
    conf         = out_buf[pred] * 100
    latest_label = f'{CLASS_NAMES[pred]} {conf:.0f}%'

    return Gst.FlowReturn.OK


# GStreamer pipeline (adjust for your camera device)
pipeline_str = (
    'v4l2src device=/dev/video0 ! '
    'video/x-raw,width=1920,height=1080,framerate=30/1 ! '
    'omxh264enc ! h264parse ! vcu_dec ! '
    'video/x-raw,format=NV12 ! '
    'appsink name=sink emit-signals=true max-buffers=1 drop=true'
)

pipeline = Gst.parse_launch(pipeline_str)
sink      = pipeline.get_by_name('sink')
sink.connect('new-sample', on_new_sample)
pipeline.set_state(Gst.State.PLAYING)

print('Pipeline running. Press Ctrl+C to stop.')
try:
    GLib.MainLoop().run()
except KeyboardInterrupt:
    pass

pipeline.set_state(Gst.State.NULL)
```
