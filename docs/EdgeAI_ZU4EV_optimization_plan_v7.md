| 事实 | 备注 |
|---|---|
| 签核是 5.000 ns，WNS +0.090 ns（`clk_out1`），无约束端点 0 | 200 MHz 是已签核的，不是推测 |
| 板上 PL 时钟由出厂固件决定，`fpga_manager` 加载 bit 不会改它 | 我在 v6 里的推断成立 |

| 在 bit 已加载时写 `PL0_REF_CTRL` 会腐蚀 fabric 状态，即使写回原值 | 之后只能「写寄存器 → 重新加载」，这条路径本身不可用于长期运行 |
| 分段计时（100 MHz）：复位 0.107、刷新 0.195、窗口 2.026、读回 0.074、Dense 0.109 ms | 复位+刷新 = 0.302 ms |

### 0.2 寄存器字段命名需要核对

`PL0_REF_CTRL = 0x01010f02`，按 ZynqMP 的 CRL_APB 布局（我凭记忆，请对 UG1087 核对）：

| 位 | 字段 | 值 |
|---|---|---|
| [24] | CLKACT | 1 |
| [21:16] | DIVISOR1 | **1** |
| [13:8] | DIVISOR0 | **15** |
| [2:0] | SRCSEL | 2（RPLL）|

1499.136 MHz ÷ (15×1) = 99.94 MHz ✓。你文档里写的是「DIVISOR0=1，DIVISOR1=15」，与你自己写的「HWH 里 DIVISOR0=4（对应 200 MHz）」不一致（标准布局下 200 MHz 的常见值是 `0x01010400`，即 DIVISOR0=4）。JSON 里的 `div1` 实际是 [13:8] 那个字段，即 DIVISOR0。**请把文档和 JSON 的字段名改正，并确认写入时 DIVISOR1 始终为 1。** 这不影响已有结果（频率确实随该字段变化），但留着错误名字会误导后来的人。

### 0.3 时钟梯度：没有一个独立的频率测量，所以不能下结论

**窗口只有两个平台：** 请求 107–125 MHz 时窗口 2.03 ms（与 99.94 MHz 相同），请求 136–187 MHz 时窗口 1.43 ms。

**用两个平台做两点拟合 [算术]：** 取 (99.94 MHz, 2.030 ms) 与 (149.9 MHz, 1.425 ms)，解得随时钟缩放的周期 ≈181 400 拍，固定部分 a ≈0.215 ms。周期与 csynth 的 175 350 拍相差约 3%，说明**这两个平台确实对应约 100 MHz 与约 150 MHz 的真实时钟**。也就是说：

- 请求 107–125 MHz 时，真实时钟没有离开 100 MHz；
- 请求 136–187 MHz 时，真实时钟都停在约 150 MHz，**187 MHz 没有出现**。

**原因未知，候选按嫌疑排序 [推断]：**

1. **MMCM。** 它是分频器与逻辑之间唯一被工具按 200 MHz 输入配置过的有源器件（倍频 6、分频 6，压控振荡器 1200 MHz）。输入 100 MHz 时压控振荡器 = 600 MHz。**据我所知** UltraScale+ 的 MMCM 压控振荡器下限约 800 MHz（请对 DS925 的 -1 速度等级核对）。如果属实，板子现在的 100 MHz 运行点本身就在 MMCM 规格之外；它恰好能锁定并稳定工作（62 万帧、1 万张逐比特一致），但这不是有保证的状态，而且输入落在设计范围之外时锁定行为可能不连续（落到错误的锁定点），与「两个平台」的现象吻合。
2. 固件/时钟框架对写入的某种限制。「读回确认」排除了「写入被忽略」，但没有排除别的钳位。
3. PS 侧其他限制。

**要点：没有硬件计数器就没有独立的频率数据，我们现在看到的所有「频率」都是由窗口反推或由寄存器算出来的。**

### 0.4 0xAA 事件：统计上不能归因于频率

`event_stats.py` 的输出（帧数用你给的数；DIVISOR 为 10 的合计按 459 610 + 500 000 帧）：

| 配置 | 事件 | 帧数 | 每百万帧 | 95% 区间 |
|---|---:|---:|---:|---|
| 100 MHz | 0 | 623 787 | 0.00 | [0, **5.91**] |
| DIVISOR 8 | 1 | 135 660 | 7.37 | [0.19, 41.07] |
| DIVISOR 10 | 1 | 959 610 | 1.04 | [0.03, 5.81] |
| 合并 | 2 | 1 719 057 | 1.16 | [0.14, 4.20] |

- 基线与其余合并的同率检验 p = 0.54；DIVISOR 8 对基线 p = 0.18；DIVISOR 10 对基线 p = 1.0。**没有证据表明发生率与频率有关。**
- **100 MHz 的 62 万帧零事件只能把发生率压到 <5.9 次/百万帧**，而合并估计值是 1.2 次/百万帧，二者完全相容。所以「100 MHz 没有这个问题」目前没有证据支持。
- 形态：字节 64–95 保持 0xAA、0–63 正常。64 字节同时是 **A53 的缓存行** 和 **64 位 AXI 的 8 拍突发**，两个候选都对得上。这一点可以用对齐偏移实验区分（§2）。

结论：**这是一个可能在任何频率都存在的、约每百万帧 1～2 次的间歇性读取异常，很可能在驱动/DMA/缓存路径上，不是频率造成的。** 在它被解释之前，任何「稳定」的结论都要附上这一条。

### 0.5 时间预算还没有闭合

分段之和：复位 0.107 + 刷新 0.195 + 窗口 2.026 + 读回 0.074 + Dense 0.109 = **2.511 ms**；实测循环间隔 2.894 ms，**有 0.38 ms 没有归属**。不做复位的 100 张间隔仍是 2.894 ms（与每帧复位的 2.889 几乎相同），说明去掉复位没有让间隔变短，**v6 里「去掉复位 −0.58 ms」的预期撤回。** 真正可去掉的是复位 0.107 + 每帧 0xAA 预填 0.195 ≈ 0.30 ms，而预填在 0xAA 问题解释清楚之前不应该去掉（它是唯一能抓到这个事件的检测）。

## 2. 决策：主线转向周期数，频率问题降级为有前置条件的支线

在当前约 100 MHz 上，各杠杆的比较（模型预测，`a` 取 0.215–0.276 ms）：

| 杠杆 | 窗口预期 | 确定性 | 风险 |
|---|---|---|---|
| **A2-L**（周期 175 350 → ≤64 758）| 2.03 → **≤0.86–0.92 ms** | 高：基于周期数，且 RF 变化已被证明不改数值 | 新 bit，要重走验证 |
| A2-M（≤46 326）| ≤0.68–0.74 ms | 高 | 面积 |
| A2-H（≤40 182）| ≤0.62–0.68 ms | 高 | 面积 |
| 时钟到约 150 MHz | 2.03 → 约 1.43 ms（已观察到）| **低**：真实频率未测、MMCM 嫌疑、0xAA 未解释、运行时写寄存器会腐蚀 fabric | 现有路径不可用于长期运行 |
| PS 路径 | 最多省 ≈0.3 ms，另有 0.38 ms 待归属 | 中 | 对硬件无风险，但受 0xAA 约束 |

**A2-L 单独就能省 ≈1.1 ms，比时钟平台的 0.6 ms 大，而且不依赖任何不确定的时钟行为。** 所以主线是：

1. **W1**（不改硬件）：0xAA 事件协议 + 时间预算闭合。
2. **W2**（硬件重整）：让 BD 与板子一致、去掉 MMCM 嫌疑、加一个 PL 计数器。
3. **W3**：在新 BD 上做 A2-L（再视面积做 A2-M）。
4. **W4**：对外材料（v6 S3）。
5. **W5**：满足前置条件后，再重开频率。

约 100 MHz 作为**当前正式运行点**。停止在运行时改 `PL0_REF_CTRL`。

## 3. W1：0xAA 事件协议与时间预算闭合（不改硬件）

### 3.1 在测试线束里加事件捕获

出现 0xAA 时立即：

1. 对同一地址再读一次（不延时），再读一次（先失效缓存/加短延时 10 µs），再读一次（1 ms 后）。三次结果都记录。
2. 读 DMA 的 S2MM 状态寄存器（Halted、Idle、DMAIntErr、DMASlvErr、DMADecErr、IOC）和 S2MM 已接收长度。
3. 保存原始 96 字节、前三帧的输出、帧序号、时间戳、当前模式（复位/不复位、缓冲位置）。
4. 把「帧数」与「事件数」写进每次运行的 JSON，供 `event_stats.py` 使用；**没有帧数就没有发生率。**

### 3.2 判读

| 现象 | 含义 | 修法 |
|---|---|---|
| 再读一次得到完整、且与 csim 一致的数据 | **PS 侧可见性**问题（缓存或顺序）| 完成后对该范围做缓存失效，或把缓冲放进非缓存映射；加内存屏障；读两次比较 |
| 长时间后仍是 0xAA，且 S2MM 长度 = 64 | 最后 32 字节没有被写入：DMA/AXIS 的 TLAST 或拍数问题 | 查 TLAST、DMA 长度、数据宽度转换 |
| S2MM 状态寄存器有错误位 | DMA 错误 | 按位处理 |
| 数据完整但与 csim 不一致 | 不是 0xAA 类问题，是数据损坏 | 回到时钟/MMCM 方向 |

### 3.3 对齐偏移实验（区分缓存行与 AXI 突发）

输出缓冲分别放在地址对 64 取余为 0、32、16 的位置，跑同样的压力循环：

- 0xAA 区间**跟着缓冲起点走**（始终是缓冲的字节 64–95）⇒ 与 DMA 突发划分有关；
- 0xAA 区间**跟着 64 字节地址边界走**（例如余 32 时落在缓冲的字节 32–95）⇒ 与缓存行有关。

### 3.4 提高发生率的压力方式（让修复能在几分钟内验证）

依次尝试：缩短 IOC 到读取的间隔；所有帧复用同一个输出缓冲；去掉预填；缓冲放在缓存行边界。目标是把发生率提到 ≥1 次/万帧。**如果找不到这种压力方式，就只能靠长跑**：发生率约 1.8 次/百万帧时，观察到 10 个事件需要约 560 万帧（`event_stats.py --need-frames 1.8`），按 2.9 ms/帧约 4.5 小时，要放进过夜计划。

### 3.5 统计规范

每个配置报告：事件数、帧数、每百万帧发生率及 95% 区间，用 `event_stats.py` 做同率检验。`0 次/N 帧` 只能写成「<3.7/N」，不能写成「没有」。

### 3.6 时间预算闭合

给循环里每一段都加计时，直到分段之和与循环间隔相差 ≤0.02 ms。必须覆盖：软复位、预填 DST、写 SRC、启动、等待、读回、解码、Dense、记录/统计、Python 循环本身。目前 0.38 ms 没有归属。预算闭合之前不要做「省时间」的结论。

**在 0xAA 事件解释清楚之前，保留每帧的 0xAA 预填与检查。** 可以先做的小改动只有一项：生产模式不做软复位（已被 1 万张逐比特一致支持），并在这个模式下重做 30 分钟 soak（100 MHz，带事件捕获），这次 soak 同时是发生率的又一个数据点。

## 4. W2：硬件重整——BD 与板子一致，去掉 MMCM 嫌疑，加 PL 计数器

目标不是更快，而是**让数字可信**。IP 本身不变，数据通路逐位不变。

### 4.1 先读（只读）

1. BD 里 PS 的 PL0 设成多少、MMCM 的输入周期/倍频/分频/压控振荡器频率、谁在使用 `pl_ref_clk`。
2. MMCM 是否真的是 1:1 直通；综合/实现日志里有没有 MMCM 的压控振荡器范围警告。
3. 对 DS925 核对 -1 速度等级的 MMCM 压控振荡器范围。

### 4.2 改动（打包成一个 RC1-I，但每项都能单独撤销）

1. **PL0 在 BD 里设成 100 MHz**，与板子实际一致，实现约束随之变成 10 ns。
2. **去掉 MMCM**（若确认是 1:1 直通），所有 IP 直接用 `pl_clk0`；若别处需要时钟向导，就按真实输入频率配置并保证压控振荡器在规格内。
3. **加一个 AXI Timer**（或等价的自由计数器），与 DMA 同一个时钟域。软件读它：
   - 频率 `f = Δcount / Δt`（PS 计时，间隔 ≥100 ms，重复 10 次）；
   - 窗口周期数 = 等待完成之后读的计数 − 启动传输之前读的计数。

这样**窗口里 PL 周期数与真实时钟都有了独立读数**，直接回答 0.215 与 0.276 的分歧，也回答 175 350 与 181 400 的分歧。

### 4.3 门

| 项 | 门 |
|---|---|
| 10 ns 下的时序 | WNS≥0（预期余量很大）|
| V1 的 KAT | 22/22 逐比特一致 |
| 1 万张 GAP | 与 RC1 **逐比特一致** |
| 窗口中位数 | 与 RC1 的 2.03 ms 相差 ≤1% |
| 计数器测得的频率 | 在 99.94 MHz 的 ±0.5% 内 |
| 计数器测得的窗口周期数 | 记录；与 csynth 的 175 350 对照 |

**如果窗口与 RC1 明显不同，说明 MMCM 或时钟路径确实有影响，这本身就是重要结论。** RC1（5 ns、带 MMCM）作为已知好的制品保留，不删除。

## 5. W3：在 RC1-I 的 BD 上做 A2-L

沿用 v6 §4.3 的流程，修正三点：

1. **实现约束用 10 ns**（与运行点一致），不要再用 5 ns 去换取用不上的裕量。HLS 的目标周期暂时保持不变，改 HLS 周期是后面单独的面积优化步骤，不与 A2-L 混在一起。
2. 计数器给出真实的窗口周期数，用它把 `latency_model.py` 的固定部分与尾部换成实测值。
3. 测试线束保留 0xAA 预填与事件捕获。

**预测（100 MHz，`a` 取 0.215–0.276，尾部取上界 27 894 拍，实测后替换）：**

| 设计 | csynth 周期（≤）| 窗口 ms | 窗口+PS ms |
|---|---:|---:|---:|
| RC1 | 175 350 | 1.97–2.03 | 2.25–2.31 |
| A2-L | 64 758 | 0.86–0.92 | 1.14–1.20 |
| A2-M | 46 326 | 0.68–0.74 | 0.96–1.02 |
| A2-H | 40 182 | 0.62–0.68 | 0.89–0.96 |

先做 A2-L，由 RC1-I 与 A2-L 两点得到每个乘法器的面积增量，再决定 A2-M/H。红线沿用：LUT<60k、DSP<500、BRAM_18K<160、WNS≥0。

**门：** 1 万张板端 GAP 与 RC1 逐比特一致（硬门）；窗口与预测对照；面积；WNS；事件捕获下无未解释的 0xAA。**与 RC1 并存，不覆盖。**

## 7. W5：重开频率的条件与做法

只有以下五条都满足才重开：

1. 有计数器测得的真实频率；
2. MMCM 已去掉或按真实输入重新配置；
3. **时钟在加载 bit 之前设置**（设备树 overlay 里的 `clocking0` 节点加 `assigned-clock-rates`，随 overlay 一起加载；或开机时由固件设置），**不再在运行时写寄存器**；
4. 0xAA 事件已解释并修复，或发生率已被量化为可接受；
5. BD 与实现约束使用目标频率（例如 150 MHz 对应 6.67 ns），多种子 WNS≥0。

做法：用计数器测量每一档的真实频率，重新拟合 `a + 周期/f`。若去掉 MMCM 之后窗口随请求频率连续变化，则 MMCM 就是平台现象的原因。**RPLL（1.499 GHz）下可取的频率有 149.9（÷10）、166.6（÷9）、187.4（÷8）MHz 等；不要使用高于签核频率的档位。**
