## 0. 读数与更正

### 0.1 必须先更正：PL 实际时钟是 99.94 MHz，不是 200 MHz

`pl0_ref` = 99 942 389 Hz [反馈]。v1 的任务书写的是 200 MHz，我在 v2–v5 里沿用了它，**所有「周期数 → 毫秒」的换算都按 5 ns 做了，在这块板上都偏小 2 倍**。周期数本身不变，毫秒要重算。具体影响：

| 之前的说法 | 更正 |
|---|---|
| v2 的「57.43 ms = 9×Σ周期/200 MHz + 0.40 ms，吻合到 0.02%」 | **作废，是错误时钟造成的巧合。** 57.397 ms × 99.94 MHz = 5.736 M 拍，是 Σ(像素×RF)=1 267 200 拍的 **4.53 倍**，不是整数。我当时把这个关系说成「指向两个结构性问题」，说重了 |
| v3 前沿表、v5 §V7.2 的毫秒预测 | 在当前时钟下全部 ×2（见附录 A 的重算表）；v5 §V7.2 的两个模型（各层求和 / 最大层重叠）也要重新评估，见 §0.3 |
| v5 的「RC1 理想单帧 0.74 ms」 | 最大层 147 456 拍 = **1.475 ms**（100 MHz），不是 0.74 ms |

好消息是：**27.41 倍是周期数之比，与时钟无关**，在两个 bit 同一时钟下测得，结论仍然成立。

### 0.2 已经确立

| 事实 | 数 | 备注 |
|---|---|---|
| 优化只改速度，函数不变 | 旧 bit 与 RC1 的 GAP 在 1 万张上逐比特一致；Top-1 都是 81.78% | 最强的回归结论 |
| 同口径加速比 | 57.397 ms → 2.094 ms，27.41 倍（bootstrap 27.41–27.42） | 口径：`start_transfer`→`wait_ioc`，不含 PS 打包与 Dense；同一 `pl0_ref` |
| 合成集 | 729 张与 csim 逐比特一致（串行解码）| 之前的全黑/灰度 0–51 错位是 **PS 解码器把真实的 0 通道当成 32 位 HP 空洞**，原始 96 字节本来就与 csim 一致，**硬件没有问题** |
| 稳定性（100 MHz 下）| 30 分钟、623 787 帧，每 100 帧比对一次共 6 238 次全部逐比特一致，0 个 0xAA 空洞 | 只有 1% 的帧被检查，但电路是确定性的，可接受；**这是 100 MHz 的证据，不覆盖更高频率** |

### 0.3 模型已经被校准，而且推翻了「各层求和」

- csynth 顶层 175 350 拍；我的阶段模型给出最大层（conv1b）147 456 拍，二者之差 27 894 拍就是其余层的填充/排空尾部 [算术]。
- 100 MHz 下：175 350 拍 = 1.754 ms；实测传输窗口 2.030 ms；**差 0.276 ms 是窗口里与 PL 计算无关的固定部分**（DMA 启动、等待完成的延迟等）[推断]。
- 各层求和模型给出 283 392 拍 = 2.834 ms，**大于实测窗口 2.030 ms，所以层间确实是重叠的**，v5 里那个「流水可能没发挥作用」的怀疑可以放下。
- 因此当前的校准模型是：

  `窗口(ms) = 0.276 + 175 350 / (f_MHz × 1000)`  （0.276 是否真的与时钟无关，由 §2 的时钟梯度检验）

### 0.4 端到端每帧的构成（100 MHz，中位数）

| 项 | ms | 来源 |
|---|---:|---|
| PL 计算（csynth 顶层）| 1.754 | 其中 conv1b 1.475，尾部 0.279 |
| 窗口里的固定部分 | 0.276 | 窗口 2.030 − 1.754 |
| 读回 96 B | 0.074 | [反馈] |
| PS Dense | 0.108 | [反馈] |
| 写输入 | 0.095 | 无 DMA 路径 0.277 − 0.074 − 0.108 [算术] |
| 每帧复位 + 缓存刷新等 | **≈0.58** | 连续 100 帧墙钟 2.889 − 窗口 2.030 − 0.277 [算术]，**是推算值，要单独测** |
| 合计（连续循环）| 2.889 | [反馈] |

**读法：** PL 计算占窗口的 86%，但按「每帧循环」算只占 61%；**每帧复位/刷新（≈0.58 ms）比整个窗口里的固定部分还大，而且它很可能不需要**（`reset_each` 与 `no_reset` 在 1 万张上已被证明逐 LSB 一致）。

### 0.5 小问题

- 表里的「传输时间」2.094 ms 与 soak 里的「传输窗口」2.030 ms 差 0.064 ms，应是计时点或复位模式的差别。不影响结论，但文档里要给出一张术语表（见 §3.5），避免以后混用。
- 「板上没有可读温度」：soak 期间没有温度记录，见 §3.3。

## 1. 下一步的优先级

| 序 | 项 | 预期收益（模型预测，非实测）| 成本 / 风险 |
|---|---|---|---|
| S1 | **核实并抬高 PL 时钟到 ~200 MHz** | 窗口 2.03 → 约 1.15 ms（PL 部分减半）| 不改硬件；风险在时序签核口径与板上稳定性，用梯度与回退控制 |
| S2 | 生产模式去掉每帧复位 + 缓存刷新优化 | 连续循环 2.889 → 约 2.31 ms（−0.58 ms）| 不改硬件；证据已有，需把 soak 在新模式下重做 |
| S3 | 补齐可对外写的材料：CPU 重测、功耗/温度、多种子、解码器回归测试 | 不改数字，改变「能写什么」| 需要测量手段 |
| S4 | A2-L（并行度提高）| 在 200 MHz 下窗口约 1.15 → 0.60 ms | 新 bit，要重走验证；到这一步固定开销已占大头 |
| S5 | 吞吐模式（DMA 排队/双缓冲）| PL-only 间隔 1.475 ms（100 MHz）→ 理论 678 FPS，200 MHz 约 1356 FPS | 需要驱动改造 |

## 2. S1：核实并抬高 PL 时钟

### 2.1 先查清为什么是 100 MHz（只读）

1. 读 `.hwh` 里 PS 的 `pl_clk0` 与各 IP 时钟的 `FREQ_HZ`，确认 BD 里设的是多少。
2. 在 Vivado 实现工程里 `report_clocks`，确认**约束的时钟周期**。
3. 读 `report_timing_summary` 的头部：+0.090 ns 的 WNS 对应哪个时钟、哪个周期。
4. `check_timing` / `report_clock_interaction`：有没有未约束路径或时钟域交叉问题。
5. 确认板子加载 bit 的方式（`fpgautil`、overlay 或你们的脚本），读 `clk_summary` 里 `pl0_ref` 的来源。

**我的推断 [推断]：** 设备树/固件（`axu4ev_factory`）在启动时按出厂设计把 PL0 设成了约 100 MHz，**通过 fpga_manager 加载新 bit 并不会应用 BD 里的时钟设置**，所以 BD 写 200 MHz、板上跑 100 MHz。

**这一步最关键的判断：** 实现时的约束周期是 5 ns 还是 10 ns。
- 若是 5 ns 且 WNS≥0（未约束路径为 0）：**200 MHz 已在慢角下签核通过**，只是板上没有跑到。
- 若是 10 ns：200 MHz 从未被签核，先用 5 ns 约束重新实现，再进入后面的步骤。
（WNS +0.090 ns 出现在 10 ns 约束下几乎不可能，所以大概率是前者，但要看报告确认，不要凭我的推测。）

### 2.2 设置时钟的三种方式（风险由低到高，选其一）

1. 设备树 overlay 里用 `assigned-clock-rates` 指定 PL0 的目标频率（或你们现有 overlay 机制里的等价写法）。
2. 通过 debugfs 写 `pl0_ref/clk_rate`（需要内核允许写）。
3. 直接写 PL0 的时钟控制寄存器（最后手段，会绕过 Linux 的时钟树，状态可能与 `clk_summary` 不一致）。

不管用哪种：设置后**读回 `clk_rate`**，并记录实际频率。可达的频率受 PLL 分频限制，以读回为准，不要按目标值记账。DMA 与 HP0 同钟，**更改时钟时 DMA 必须空闲**。

### 2.3 时钟梯度

从当前 99.94 MHz 起，依次到约 120、150、171、200 MHz（取 PLL 实际能设到的值）。每一档：

1. V1 的 KAT（22 个已知答案）全部逐比特一致；
2. 前 1000 张与黄金 GAP 逐比特一致；
3. 窗口延迟（≥1000 帧，中位数/p99）；
4. 一行写入 `ladder.csv`（`f_mhz,window_ms`）。

任何一档出现不一致：立即回到上一档，记录现场，**不要继续升频**。

### 2.4 拟合与判读

```bash
python3 latency_model.py fit --csv ladder.csv
```

| 拟合结果 | 含义 |
|---|---|
| 固定部分 ≈0.28 ms，周期 ≈175 k，R²≈1 | 模型成立：`窗口 = 0.276 + 175350/f`，固定部分与时钟无关 |
| 固定部分随频率明显变化（残差有趋势）| 窗口里有随时钟缩放的第三项（如 DMA 端），按分量重新建模 |
| 周期远小于 175 k | 窗口里 PL 以外的部分更大，S4 的收益要下调 |

### 2.5 选定目标频率 f* 的门

| 项 | 门 |
|---|---|
| 1 万张板端 GAP 对黄金 | 逐比特一致 |
| 30 分钟 soak（在 f* 下，每 100 帧比对）| 全部一致，0 个 0xAA 空洞 |
| 签核 | 实现约束周期 ≤ 1/f*，WNS≥0；多种子（S3）WNS 全部≥0 |
| 温度 | 有外部测温手段则记录；没有就明确写「未测」|

通过后：RC1 在 f* 下成为 **RC1@f***；100 MHz 的配置作为安全回退保留。**之后所有延迟数字必须同时写频率。**

### 2.6 预期（模型，要由 §2.4 验证）

窗口：99.94 MHz 2.031 ms → 150 MHz 1.445 → 171.3 MHz 1.300 → 199.9 MHz 1.153 ms。固定的 0.276 ms 不随时钟缩放时，升频的收益上限就是 PL 部分减半。

## 3. S2 与 S3：不改硬件就能做的事

### 3.1 S2：每帧复位与缓存刷新（≈0.58 ms 的推算值）

1. **先测，不要信推算：** 把循环拆成几段单独计时：软复位、缓存刷新（或无效化）、写输入、启动与等待、读回、Dense。输出一张分项表替换上表里那个 0.58。
2. **生产模式 = 不复位。** 已有证据：每帧复位与不复位在 1 万张上逐 LSB 一致。要补的是：在不复位模式下重做 30 分钟 soak，每 100 帧与黄金比对，并在每次会话开头跑 KAT。
3. **缓存：** 只刷新被写过的范围；或把缓冲放在非缓存/一致性映射的内存里；确认读回缓冲在读之前被无效化。
4. **驱动：** 把 Python 里每帧的对象分配和打包挪到 C 或预分配缓冲；目标是「写输入 + 读回 + Dense」从 0.277 ms 降到 ≤0.15 ms。
5. 预期：连续循环 2.889 → 约 2.31 ms（仅去掉 0.58），再配合驱动优化可再降。

### 3.2 S3：CPU 重测

在 A53 上用同一份 `cifar10_bench_10k.npz`、同一顺序重跑 TFLite INT8（线程数写明），重复 3 次；记录计时口径（是否含预处理、是否含 Dense），输出与 FPGA 同格式的 JSON。**对外的「比 CPU 快 N 倍」只用同口径、同数据的数字。** 口径要对得上：FPGA 的 2.094 ms 不含 PS 打包与 Dense，和 CPU 比时要用端到端口径（含这两项）。

### 3.3 S3：功耗与温度

- 功耗：板外在线功率计（12 V 输入），空闲、CPU 基线、FPGA 运行各 60 秒，至少 3 次，用「运行 − 空闲」。没有手段就写「未测」，不要估算。
- 温度：板上没有可读温度时，用外部测温（红外/热电偶贴散热片），soak 前后各记一次；这是在更高频率下做 soak 的必要记录。

### 3.4 S3：多种子布线

在**目标频率的约束周期**下用 3–5 个不同的策略/种子重跑布线，汇总 WNS、TNS、WHS、脉宽余量；任何一个为负就换策略。100 MHz 下的 soak 与 WNS 不能代替这一步。

### 3.5 S3：解码器回归测试与术语表

1. **解码器回归测试（根因就在这里）：** 单元测试覆盖 96 字节输出里每个通道位置取 0、取随机值、取接近 0xAA 的模式；断言串行解码路径**从不**调用 HP 空洞启发式。把全黑图并入 KAT（现在它应当通过）。
2. **术语表（写进 `docs/STATUS.md`）：**

| 名称 | 起止 | 现值 |
|---|---|---|
| 传输窗口 `T_window` | `start_transfer` → `wait_ioc` | 2.030 ms（soak）|
| 传输时间（1 万张表）| 同上但计时点略有差异，需注明 | 2.094 ms |
| PS 部分 `T_ps` | 写输入 + 读回 + Dense | 0.277 ms |
| 循环间隔 `T_loop` | 连续两帧的墙钟差 | 2.889 ms（含复位与刷新）|

3. `BitExact=1` 最小复现（低优先级，v5 §V8.3），留作升级 hls4ml 时的回归。

## 4. S4：A2-L（视需要）

| A2-L（RF 27/36/144/90/180/216）| 99.9 | ≤64 758 | ≤0.924 | ≤1.201 | 0.369 |

### 4.2 Amdahl：为什么 A2-L 之后不再值得加并行度

在 200 MHz 下，A2-L 的端到端（窗口+PS）≈0.88 ms，其中窗口里的固定部分 0.276 加 PS 0.277 已经是 0.55 ms，**占 63%**。再升到 A2-M，窗口只再省约 0.09 ms。想继续降端到端延迟，下一步应该是 S2/S5（PS 与 DMA 路径），而不是更多乘法器。

### 4.3 若做，沿用 v5 §V7.3 的流程，并修正两处

1. 转换日志无 `Invalid ReuseFactor`；csim 前 1000 张 GAP 与 RC1 **逐比特一致**。
2. csynth：每层 `ReuseLoop` II=1；顶层周期与 §4.1 对照；**把真实尾部代入 `latency_model.py project --tail-cycles`**，替换我给的上界。
3. 综合/布线用**目标频率的约束周期**；LUT/DSP/BRAM/WNS 写入 JSON；由 RC1 与 A2-L 两点估计每个乘法器的面积增量。
4. 板端：V1 自检 → 1 万张，**GAP 与 RC1 逐比特一致（硬门）**；窗口延迟与 §4.1 对照，回填梯度拟合的固定部分。
5. 与 RC1 并存，不覆盖，A/B 对照同 V2。

停手：窗口改善 <15%；或面积超红线；或 WNS<0；或 GAP 不再与 RC1 一致。

## 5. S5：吞吐模式（可选）

现状：DMA 不能排队，所以循环间隔 2.889 ms 不是 PL 流水间隔（PL 间隔约等于最大层周期，100 MHz 下 1.475 ms，约 678 FPS）。

1. 改造：S2MM 使用描述符环（SG）或多缓冲，MM2S 在上一帧未返回时就提交下一帧；PS 的打包/Dense 与 PL 计算重叠。
2. 门：1 万张按顺序全部逐比特一致（没有帧丢失、没有帧错位——**帧序错位会在逐帧比对里立刻暴露**）；不同队列深度（2、4、8）各测一次吞吐。
3. 预期上界：`min(1/PL 间隔, 1/PS 每帧)`。RC1@200 MHz：PL 间隔 0.738 ms，约 1356 FPS，PL 受限；A2-L@200 MHz：PL 间隔 0.184 ms，但 PS 每帧约 0.28 ms，约 3600 FPS，PS 受限。

只有当目标里包含吞吐（而不只是单帧延迟）时才做。

## 6. S6：精度线（与上面互相独立）

硬件与 Keras 相差 0.12 点，所以 Keras 域的训练改进可以直接转化为板端精度。

| 项 | 状态 / 做法 |
|---|---|
| B1（Q8）| 关闭（+0.34 点，p=0.130）|
| B0 | 同架构的训练改进：更强的老师、KD 的 α/T 重扫、数据增强、更长训练。判据：1 万张配对检验 p<0.05 且净增 ≥1 点，以 csim 为准 |
| B2 | 加宽，先 24/28/32（MAC 约 2.06×）。**现在有两个面积点可以估计增量（RC1 与 A2-L），再决定是否装得下；时钟升到 200 MHz 后算力裕量也更大** |

改了权重就要重新转换/综合，所以最好与某次硬件改动合并，并把 §3.5 的解码器回归测试和 KAT 一起重做。

| 项 | 门 | 失败怎么办 |

| S1 | 梯度每档 KAT+1000 张一致；f* 下 1 万张逐比特一致；30 分钟 soak 一致；签核 WNS≥0 | 回到上一档；约束周期不对就重新实现 |
