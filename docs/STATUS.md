## 时钟（v6 S1）（已被 X1–X4 取代）

布线时序报告与 RC1 是同一次实现：`clk_pl_0` 和 `clk_out1_system_pl_ref_clk_0` 都是 5.000 ns / 200 MHz，WNS +0.090 ns 在 clk_out1 上，内部无约束端点为 0。签核到 200 MHz，没有往上加。HWH 里的 MMCM 是 6/6，输出等于 `pl_clk0`。HWH 里的 DIVISOR0=4 是按另一套源频率算的，不能写到当前这颗 RPLL 上。

板上 RPLL 一半是 1.499 GHz。`PL0_REF_CTRL = 0x01010f02`。按 UG1087（PL0_REF_CTRL）：CLKACT 是 [24]，DIVISOR1 是 [21:16]，DIVISOR0 是 [13:8]，SRCSEL 是 [2:0]。所以这颗寄存器是 DIVISOR0=15、DIVISOR1=1、SRCSEL=2（RPLL），1499.136÷(15×1)=99.942 MHz。先前 JSON 里的 `div1` 写的是 [13:8]，那个字段的名字是 DIVISOR0，DIVISOR1 一直是 1。HWH 里 DIVISOR0=4 与这个布局一致，只是它按另一套源频率算，不能写到当前 RPLL 上。debugfs 的 `clk_rate` 只读，写完寄存器后仍停在 99942389，不能拿它当实测频率。

DS925（2026-07-09，1.30）表 1：-1 速度等级在 0.85 V 和 0.72 V 两列的 MMCM_FVCOMIN 都是 800 MHz，FVCOMAX 都是 1600 MHz。本器件是 xczu4ev -1。MMCM 按 199.998 MHz 输入配成倍频 6、分频 6，设计压控振荡器是 1200 MHz；输入落到 99.942 MHz 时压控振荡器是 600 MHz，低于 800 MHz。当前 100 MHz 运行点在 MMCM 规格外。

在 bitstream 已经加载时写这个寄存器，即使写回原来的 15，GAP 也会错到约 1200 LSB。重新加载同一份 RC1 后恢复逐比特一致。所以每次改分频都是先写寄存器、再重新加载、确认读回。失败时写回 15 并重新加载。X4 成功后板子留在 DIVISOR0=10。

分频读回和传输窗口不是同一件事。窗口只有两档：

| DIVISOR0（[13:8]，先前误记成 div1） | 按寄存器算出的频率 | 1000 张或 40 张窗口中位数 | max LSB |
|---|---|---|---|
| 15 | 99.94 MHz | 2.033 ms | 0 |
| 14、13、12 | 107 / 115 / 125 MHz | 仍是 2.025 ms | 0 |
| 11、10 | 136 / 149.9 MHz | 1.422–1.425 ms | 0 |
| 9、8 | 167 / 187 MHz | 仍是 1.428 ms | 0 |

按寄存器频率去拟合 `window = a + cycles/f`，得到 a=0.571 ms、cycles=153504、R²=0.80，残差从 −0.17 到 +0.23 ms。这不是一条过关的拟合。只有 99.94 MHz 和大约 150 MHz 这两档对得上 175350 拍：99.94 MHz 上固定部分约 0.27 ms，149.9 MHz 上预测窗口 1.44 ms，实测 1.425 ms。中间和更高的分频没有给出第三个独立频率，不能把 187 MHz 记成实测。

DIVISOR0=8 的寄存器设置下，1 万张 max LSB 为 0，窗口中位数 1.430 ms。这是上面那一档更快的窗口，不是 187 MHz 的周期数。随后 135660 帧出现 0xAA。把分频留在 10（窗口同样是 1.42 ms）再跑，459610 帧时通道 16–23 仍是灌进去的 0xAA，通道 0–15 是正常值。96 字节输出里这 8 个通道正好从第 64 字节开始，对齐 A53 的一条 cache line。接着在同一分频上再跑 50 万帧，没有再现。100 MHz 那次 30 分钟、623787 帧没有这种现象。这一段是 500 µs 轮询口径下的记录。官方运行点改到 149.9136 MHz 见 X4，依据是后来的忙等梯度和 380 万帧。

## W1（99.942 MHz，没有写 PL0_REF_CTRL）

有一次线束没清掉上一帧的 IOC，整段 96 字节在第一次读和 10 µs 后再读时都还是 0xAA，1 ms 后再读已经不是。S2MM 状态是 `0x00001000`（只有 IOC），长度 96，没有错误位。这是把旧的完成标志当成了新传输，不是先前那种只剩字节 64–95 的事件。重新加载同一份 RC1 之后，200 张四种计时组合都恢复 max LSB 0。加载没有改 `PL0_REF_CTRL`，读回仍是 `0x01010f02`。

## X2（2026-10-25，C 热路径，99.942 MHz）

热路径是交叉编译的 aarch64 程序。每帧预填 0xAA，拷贝输入，清掉 MM2S 和 S2MM 的 IOC 并读回为 0，再启动；完成后要求 S2MM 无错误位、长度 96、IOC 置位，才读 96 字节。解码按串行 int16/1024，稠密层用与 Python 相同的 float32 权重。启动时软复位一次，帧内不再复位。没有写 `PL0_REF_CTRL`。

1 万张与 RC1 黄金 GAP 逐比特一致，C 的 argmax 与这份黄金 GAP 的 numpy 稠密层逐样本相同，所以 Top-1 仍是先前的 81.78%。KAT 19 张同样 max LSB 0。

10k 与 30 分钟 soak 的分段中位数相同，分段之和与循环间隔相差 0.0003 ms：

| 段 | ms |
|---|---:|
| poison | 0.0007 |
| src | 0.0038 |
| idle-check | 0.0017 |
| start | 0.0016 |
| wait | 1.6838 |
| read | 0.0017 |
| decode | 0.0005 |
| dense | 0.0040 |
| 合计 / 循环 | 1.6979 / 1.6982 |

不含 wait 的 PS 路径是 0.0117 ms，低于 0.15 ms 的门。`T_hot` = src + start + wait + read + decode + dense = 1.695 ms。Python 生产路径是 2.484 ms。

## X3（2026-10-25，99.942 MHz，没有写 PL0_REF_CTRL）

IOC 置位后立刻读输出的最后 8 字节，再隔 10 µs 读整段 96 字节。10 万帧和随后 270 万帧都是：第一次读已经不是 0xAA，立刻读到的 GAP 与黄金一致，10 µs 后再读没有一个字节不同。假设「IOC 早于最后一个突发落到内存」在这套 O_SYNC 映射上没有出现。

10 万帧的采样延迟（IOC 到第一次尾部读取，数据当时已经可见）：中位数 180 ns，p99 480 ns，最大 6.2 µs。270 万帧里有 2 帧的采样晚了 100–200 µs（最大 136 µs），读到的时候尾部同样已经不是哨兵。这是 CPU 晚去读，不是数据晚到。

因此没有加「读之前再等一会儿」的修复。

100 MHz 上累计 0 事件的帧：先前 1 252 130，加上 C 生产 soak 1 059 467，再加上这次带双读的 2 800 000，共 5 111 597。Garwood 95% 上界 0.72 次/百万帧。其中 C 生产路径（X2 soak 与这次双读）3 859 467 帧，上界 0.96 次/百万帧，低于 1 次/百万帧。与更高分频上的 2 次/1 095 270 帧做同率检验，p = 0.031。事件本身仍没有被复现，机理没有改写。149.9 MHz 上的同样长跑见 X4。记录在 `results/opt_v2/v8_x3_delay.json`。
