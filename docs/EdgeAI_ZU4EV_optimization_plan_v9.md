### 0.2 我对 X1 的预测成立了

6 个频率点的忙等 `T_wait` 与 `1.719×99.942/f` 的偏差在 +0.18%…+1.93%，拟合 R²=0.99979，固定部分 0.027 ms，周期 169 590。v8 把「两个平台」解释为 500 µs 轮询量化，这个解释被检验通过；v7 的「钳位/MMCM 错误锁定」已经完全放弃。**X1 同时给出了更重要的东西：时钟确实跟着寄存器走，136–187 MHz 的 MMCM 合规区间里 1000 张逐比特一致。**

### 0.3 0xAA：现在能说什么，不能说什么

**X3/X4 给出的硬事实：**
- C 线束、100 MHz：累计 3 859 467 帧，0 事件；C 线束、149.9 MHz：3 800 000 帧，0 事件（尾部 8 字节在 IOC 之后第一次读就已经不是哨兵，10 µs 后再读无差异）。
- 「IOC 先于最后一个突发落到内存」（我在 v8 的假设 HX）**在两个时钟上都没有出现**，所以不再作为主假设。

**需要纠正的推断：** X3 写的 p = 0.031、X4 写的 p = 0.050，比较的是「C 线束在 100/150 MHz 的零事件」对「历史上 Python 线束在更高频率下的 2 次事件」。**这两组之间不仅频率不同，线束也不同**（Python 与 C；500 µs 轮询与忙等；有没有清 IOC 并验证；有没有检查长度/状态位；以及那两次事件发生在反复写时钟寄存器并重新加载之后的会话里）。所以 p 值只能说「C 线束明显好于旧线束」，**不能说是时钟造成的，也不能说与时钟无关**。

要把这件事真正归因，缺的是 2×2 表里没测过的那一格：

| | Python 旧线束 | C 线束 |
|---|---|---|
| 99.94 MHz | 0 / 1 252 130 | 0 / 3 859 467 |
| 149.9 MHz | 历史上 2 次 / 1 095 270（DIVISOR 8 与 10，都在写寄存器、重新加载的会话里）| 0 / 3 800 000 |

**缺失的一格是「Python 旧线束 × 149.9 MHz」。** 做法见 §5。

### 0.4 时序裕量的正确读法

签核在 5 ns（200 MHz）。运行点是 149.9136 MHz，周期 6.671 ns。最差路径约 `5 − WNS`：RC1 4.910 ns，A2-L 4.952 ns [算术]。所以**运行点上的真实余量约 1.76 ns（RC1）和 1.72 ns（A2-L），约占周期的 26%**，WNS +0.048 ns 只是 200 MHz 约束下的数，不是运行点上的数。保持时间余量（WHS +0.006…+0.010 ns）与频率无关，由工具在最快角检查，降频不会改善它。

### 0.5 A2-L 的几个读数

- csynth 顶层 51 762 拍，比我在 v7/v8 给的上界 64 758 小，尾部从 27 894 降到约 14 898 拍。
- 实测等待对应的周期数：(0.3837 − 0.027)×149.9136 MHz ≈ 53 470 拍，比 csynth 高 3.3%；RC1 是低 3.3%（169 590 对 175 350）。**csynth 的周期估计大约是 ±4% 的量级，方向不固定**。
- DSP 保持 207，说明新增乘法器落在 LUT 里；LUT 增量 11 233 / 68 个 ≈ **165 LUT/个**。
- **A2-M 与「定向加 P」都不值得做** [算术，按 165 LUT/个外推，假设 §7 的尾部不变]：

| 方案 | ΣP | 顶层周期（估）| `T_wait`（估）| LUT（估）|
|---|---:|---:|---:|---:|
| A2-L（已上板）| 188 | 51 762（实）| 0.384（实）| 44 692（实）|
| A2-L+（RF 9/24/72/90/180/216）| 272 | ≈39 474 | ≈0.29 ms | ≈58 600 |
| A2-M（RF 9/18/72/60/180/216）| 324 | ≈33 330 | ≈0.25 ms | ≈67 100 |

A2-L+ 用 +31% 的 LUT 换 −24% 的等待，绝对节省只有约 0.09 ms；A2-M 超过 60 000 LUT 红线。**停在 A2-L。**

## 2. R1：A2-L 发布验证（命名 RC2）

RC2 = `results/opt_v2/a2l/cifar10_accel.bit`，MD5 `395160123c39a98d478e598c9f93e39e`。已知良好版（`46987907…`）与 RC1（`334e2745…`）不动。

| 检查 | 做法 | 门 |
|---|---|---|
| 合成集 729 张 | 板端（C 线束，149.9 MHz）对 A2-L 的 csim，逐比特 | 全部一致，max LSB 0 |
| 长跑 | C 线束 + 尾部读取 + 10 µs 双读，**≥1000 万帧**，约 66 分钟（0.397 ms/帧）| 0 事件；0 次的 95% 上界 ≈0.37 次/百万帧 |
| 多种子 | 5 ns 约束下 ≥3 种策略（默认已有 +0.048）；**另加一次 6.667 ns 约束**，作为运行点上的签核 | 全部 WNS≥0；6.667 ns 下 WNS 预期 ≈+1.7 ns |
| 冷启动 | 断电重启 → 启动脚本 → KAT → 100 帧 → 运行 | 全部通过 |

## 3. R2：CPU 同口径重测与最终 A/B

### 3.1 CPU 重测

A53 上用同一份 `cifar10_bench_10k.npz`、同一顺序，TFLite INT8，重复 3 次，写明线程数。给出两个口径：

| 口径 | 含义 |
|---|---|
| 仅推理 | 只计 `invoke` |
| 端到端 | 从 uint8 图像到类别（含输入量化与取最大值）|

FPGA 一侧对应的是 `T_hot`（写 6144 B 输入 + 启动 + 等待 + 读回 + 解码 + 稠密层）。**CPU 的 12.23 ms 与 83% 是早期数字，样本数与条件不明，不能直接用。** 另外 CPU 模型与 FPGA 模型不是同一个网络（83% 对 81.78%），表里必须同时给出精度。

## 4. R3：功耗与温度

- 功耗首选板外在线功率计（12 V 输入）。三个状态各测 60 秒、至少 3 次：空闲、CPU 基线持续运行、FPGA 持续运行（C 线束）。用「运行 − 空闲」。
- **注意 C 线束是忙等：** FPGA 运行时 A53 在空转，系统功耗里混入了 CPU 自旋的部分。要么同时报告「系统 ΔP」并注明忙等，要么另做一个用中断或睡眠等待的版本来隔离 PL 的贡献。J/帧 = ΔP / 持续帧率。
- 温度：板上没有可读温度。先查 `/sys/bus/iio` 与 `hwmon` 是否有可用节点；没有就用外部测温（红外/热电偶贴散热片），在长跑前后各记一次。
- 没有测量手段就写「未测」。Vivado 的 `report_power`（无向量估计）只能作为带标注的估计，不能与实测并列。

## 5. R4 与 R5

### 5.1 R4：运行点守卫与可复现性

1. **启动脚本**：写 `DIVISOR0=10`（`DIVISOR1` 保持 1，其余位不动）→ 立刻重新加载 → 读回 `0x01010a02` → KAT → **等待时间检查**（RC2 应在约 0.384 ms ±5%，99.94 MHz 时会是约 0.56 ms，用来抓「时钟没设」）→ 记录 MD5 与时钟读回。
2. 铁律：**不允许在 fabric 已加载并运行时写 `PL0_REF_CTRL`**。
3. 每次长跑开始和结束都读 `PL0_REF_CTRL`，写进结果 JSON。
4. 从 h5 一键干净重建：转换 → csynth → 比对 `parameters.h`/`defines.h` 与冻结版本逐字相同 → 每层周期相同。`vivado_project_a2l` 是拷贝工程，要确认重建脚本能重现它。
5. **RTL cosim**（A2-L）：给出含填充位置的真实周期（实测约 53 470 拍对 csynth 51 762）和帧间隔，后者是 §5.3 吞吐模式的依据。
6. `BitExact=1` 的最小复现（低优先级）：同一个 h5、同一批 256 张，两种转换的 csim GAP 对 Keras 的 MAE/Top-1，加上各 BN 流位宽。

### 5.2 R5：0xAA 收尾（补上缺失的那一格）

1. 先查日志：那两次事件发生时线束的模式（复位/不复位、500 µs 轮询还是忙等、有没有清 IOC、前面做了多少次「写寄存器 + 重新加载」）。
2. **Python 旧线束 × 149.9 MHz**，500 µs 轮询，≥200 万帧（按约 2.4 ms/帧约 80 分钟）。若历史发生率 1.83 次/百万帧成立，期望 3.7 次，零事件的概率约 2.5%。
3. 结果的读法：

| 结果 | 含义 | 下一步 |
|---|---|---|
| 事件复现 | 与旧线束（和/或频率）有关 | 把 C 线束的保护一项项加回 Python 线束（清 IOC 并验证、长度/状态位检查、尾部读取），看哪一项让事件消失 |
| 零事件 | 历史事件不是旧线束在该频率下的稳态行为，更可能与当时「反复写寄存器 + 重新加载」的会话状态有关 | 记入已知问题，继续保留哨兵与尾部检查，不再追 |

4. 统计一律用 `event_stats.py`，并且**只比较同一线束、同一条件的帧**。
5. 对外的写法：「C 线束在两个时钟上累计 765 万帧零事件；历史上旧线束出现过 2 次，机理未明。」

## 6. R6：吞吐模式（可选，不改硬件）

A2-L 的单帧循环 0.397 ms 是串行的：PL 在 PS 的 0.011 ms 和排空的尾部里是空闲的。PL 的帧间隔等于最慢一级的周期，约 36 864 拍（149.9 MHz 下 0.246 ms，约 4 066 FPS），所以有大约 60% 的吞吐空间。

做法（假设 DMA 是简单模式，没有 SG）：两个通道相互独立。MM2S 在上一帧的 MM2S 完成后立即发下一帧，S2MM 在上一帧完成后立即重新装载。IP 是自由运行的数据流，下一帧的输入可以在上一帧尚未排空时进入。

| 项 | 门 |
|---|---|
| 顺序 | 1000 万帧按顺序逐比特一致，帧序错位会在逐帧比对里立刻暴露 |
| 事件 | 事件捕获开启，0 个未解释事件 |
| 吞吐 | 报告队列深度 1、2 的 FPS 与单帧延迟 |
| 先决 | §5.1 的 cosim 给出帧间隔，确认约 0.246 ms |

只有目标里包含吞吐才做。

## 7. R7：精度-延迟折中（可选）

现在硬件与 Keras 只差 0.12 点，所以 Keras 域的训练改进可以直接转化为板端精度。B1（Q8）已关闭。

**B0（不改架构）先做**：更强的老师、KD 的 α/T 重扫、数据增强、更长训练，判据 1 万张配对检验 p<0.05 且净增 ≥1 点。

**B2（加宽）**：以 `rf_planner.py --widen` 与 §0.5 的 165 LUT/个估算（只是粗估，宽网每个乘法器的外围开销可能更大）：

| 设计 | ΣP | 顶层周期（估）| `T_wait`（估）| MAC | LUT（估）|
|---|---:|---:|---:|---:|---:|
| A2-L（已上板）| 188 | 51 762 | 0.384 ms | 5.07 M | 44 692 |
| 加宽 24/28/32，RF 27/54/216/126/252/288 | 268 | ≈70 194 | ≈0.50 ms | 10.43 M | ≈57 900 |

即用约 1.3 倍的等待换 2.06 倍的 MAC，LUT 接近红线。**只有 B0 / 训练实验显示加宽能带来 ≥1.5 点（配对检验）才值得做**，并且先用 csynth + `export_design -flow syn` 核对面积，再决定是否实现。尾部周期沿用 A2-L 的约 14 898 拍只是假设。

## 8. R8：文档与对外材料

## 我不能判断的几点

1. **csynth 的周期估计**在 RC1 上偏高 3.3%、A2-L 上偏低 3.3%，我没有看到逐层数据，不知道是哪一层造成的；cosim 会给出答案。
2. **吞吐模式**假设 DMA 是简单模式且 IP 是自由运行的数据流；若 IP 有每帧的启动握手，§6 不成立。
3. **加宽网络每个乘法器的 LUT 成本**，165 来自 A2-L 与 RC1 之差，宽网可能更高。
4. **0xAA 历史事件当时的线束细节**我看不到；§5.2 第 1 步要靠你们的日志。
5. **CPU 基线**的模型、线程数、预处理口径，我不知道现有的 12.23 ms 是怎么测的。
