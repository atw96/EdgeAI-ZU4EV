## 0. 读数，以及一处我必须收回的解释

### 0.1 手册核对的两个结论

| 项 | 结论 |
|---|---|
| 寄存器字段 | DIVISOR0=[13:8]=15，DIVISOR1=[21:16]=1，SRCSEL=2。先前的 `div1` 就是 DIVISOR0，已改名。无需再议 |
| MMCM | -1 速度等级压控振荡器范围 800–1600 MHz；当前 6/6 配置在 200 MHz 输入时 1200 MHz。**99.942 MHz 输入对应 600 MHz，在规格之外** [反馈]。反过来：输入 ≥133.3 MHz 才合规 [算术]，签核上限 200 MHz，所以**对现有 BD 来说，合规且已签核的频率区间是 [133.3, 200] MHz**；100 MHz 运行点不在其中 |

100 MHz 上的 125 万帧零事件、1 万张逐比特一致说明它「恰好能用」，但这不是有保证的状态，对外要写明。

### 0.2 我收回 v7 §0.3：两个「频率平台」是轮询量化，不是时钟被钳位

v7 把窗口 2.03 / 1.43 ms 当成连续测量，推出「真实时钟只有约 100 和约 150 MHz，187 MHz 没有出现」，并把 MMCM 错误锁定列为头号嫌疑。**W1 的预算表显示这个读法是错的。** 之前所有窗口都是在 500 µs 睡眠轮询下测的：

| 模式 | 等待（wait）| 来源 |
|---|---:|---|
| 500 µs 轮询 | 1.860 ms | [反馈] |
| 忙等 | 1.719 ms | [反馈] |

1.860 = 3 × 0.62 [算术]：500 µs 的睡眠实际间隔约 0.62 ms（睡眠精度、系统调用、Python 开销），轮询只能在 0.62、1.24、1.86、2.48 ms 处发现完成。窗口 = 启动 0.149 + 轮询等待 + 约 0.017，于是：

- 等待落在 (1.24, 1.86] ⇒ 窗口 2.026 ms（旧 bit 的 2.03）；
- 等待落在 (0.62, 1.24] ⇒ 窗口 1.406 ms（观察到 1.422–1.430）。

**两个平台之差 0.60 ms 就是一个轮询步长。** 用忙等基准 1.719 ms @99.942 MHz 按 1/f 缩放，`latency_model.py ladder` 的预测是：

| DIVISOR0 | f (MHz) | VCO (MHz) | MMCM | 忙等等待 (ms) | 轮询下看到的窗口 (ms) | 观察到 |
|---:|---:|---:|---|---:|---:|---:|
| 15 | 99.94 | 600 | 规格外 | 1.719 | 2.026 | 2.026–2.033 |
| 13 | 115.3 | 692 | 规格外 | 1.490 | 2.026 | 2.03（12–14 档）|
| 12 | 124.9 | 750 | 规格外 | 1.375 | 2.026 | 2.0305 |
| 11 | 136.3 | 818 | 合规 | **1.261** | 2.026 | 1.42（边界）|
| 10 | 149.9 | 900 | 合规 | 1.146 | 1.406 | 1.4249 |
| 9 | 166.6 | 999 | 合规 | 1.031 | 1.406 | 1.4278 |
| 8 | 187.4 | 1124 | 合规 | 0.917 | 1.406 | 1.4281 / 1.4303 |

预测与观察在 1.5% 以内，只有 DIVISOR0=11 是边界（预测等待 1.261 比最近的轮询点 1.24 高 2%，在误差内，需要忙等测量裁决）。**这个解释比「时钟被钳位在 150 MHz」简单得多，也不需要 MMCM 错误锁定。** 它是 [推断]，但有一个很便宜的检验：把梯度用忙等重做，预测值已经列在上表（§2）。

**因此撤回：** v7 的两点拟合（181 400 拍、0.215 ms）、「187 MHz 没有出现」、「MMCM 错误锁定」的推测。两点拟合的输入本身就是被量化污染的窗口。v6/v7 里的固定部分 0.215–0.276 ms 同样作废。

### 0.3 真正的时间结构（忙等，99.942 MHz，中位数）

| 项 | ms | 归类 |
|---|---:|---|
| **wait（PL 计算 + DMA 完成）** | **1.719** | 硬件 |
| decode（`decode_gap_raw`）| 0.279 | PS |
| src（写 6144 B 输入）| 0.151 | PS |
| start（启动传输的寄存器写）| 0.149 | PS |
| book（记账）| 0.140 | 线束 |
| idle-check | 0.114 | 线束 |
| dense | 0.111 | PS |
| read（读回 96 B）| 0.075 | PS |
| poison（0xAA 预填）| 0.069 | 线束/哨兵 |
| between | 0.042 | 线束 |
| **合计 / 间隔** | 2.849 / 2.855 | 缺口 0.006 |

- 1.719 ms × 99.942 MHz = 171 800 拍，与 csynth 的 175 350 拍相差 2% [算术]。**csynth 顶层周期可以直接当作预测依据（打 0.98 折）。**
- 窗口里的固定开销只剩启动的 0.149 ms，没有 v6/v7 假设的 0.215–0.276 ms。
- **PS 侧不是 0.277 ms，而是 1.128 ms（占循环的 40%）。** 其中生产路径（src + start + read + decode + dense）= **0.765 ms**；只在验证线束里才有的部分（idle-check + poison + book + between）= 0.365 ms。v6/v7 里用的「PS 0.277 ms」是只含部分项的数，低估了约 4 倍。
- 去掉每帧软复位后间隔 2.855 ms（忙等），与带复位 2.918 的差只有 0.07 ms。**复位不是问题。**

### 0.4 0xAA 事件：现状

- 正常路径、不失效、不预填、地址对 64 取余 0/32/16，各 2 万帧：0 事件。30 分钟不复位 soak：628 343 帧，0 事件，max LSB 0。
- 0 事件的 95% 上界：这次 soak 5.87 次/百万帧；与早上的 0/623 787 合并 2.95 次/百万帧。
- 把全部 100 MHz 帧（1 252 130，0 事件）与更高请求频率的两次事件（共 1 095 270 帧）放在一起：同率检验 **p = 0.22**（DIVISOR 8 对基线 p = 0.098，DIVISOR 10 对基线 p = 0.43）。趋势指向「事件只在更高频率出现」，但证据仍然不足。要让这个对比达到 p<0.05，100 MHz 一侧大约还需要 **380 万帧零事件** [算术]。
- **驱动是 `/dev/mem` + `O_SYNC` 映射，CPU 缓存不介入。** 这使「A53 缓存行里留着旧的 0xAA」的候选基本消失（不去失效仍然 max LSB 0 也支持）。64 字节边界现在更可能对应 **AXI 突发**，或者「读得太早」。
- **W1 找到一个线束级的失败模式：上一帧的 IOC 没清，下一帧立刻判完成，读到整段 0xAA。** 这证明「过早读取」可以产生 0xAA。历史事件只有字节 64–95 是 0xAA，意味着读取恰好发生在输出写入的途中，这类「抓到半截」的窗口极窄，与约 1 次/百万帧的稀有度相符。这是一个**更具体、可检验的假设**（§3）。

### 0.5 之前的 27.41 倍也被量化污染

新 bit 的 2.094 ms 是轮询量化后的值，忙等下窗口 = 0.149 + 1.719 = 1.868 ms；旧 bit 的 57.397 ms 量化误差只有 1% 量级。**同口径的 A/B 要在忙等下重做**，预期比值约 30 倍（57.1/1.868）[算术/推断]。27.41 倍作为「500 µs 轮询口径下」的数字仍然有效，但会低估。

## 2. X1：用忙等重做时钟梯度（不改硬件，约半个会话）

**流程（每个分频值）：** 确认 DMA 空闲 → 写 DIVISOR0（DIVISOR1 保持 1，其余位不动）→ **立即重新加载 RC1**（不允许在加载状态下继续跑）→ 读回寄存器 → KAT（22/22）→ **忙等**测量 1000 帧，同时记录 `wait` 与窗口的中位数/p99 → 前 1000 张与黄金 GAP 比对（max LSB）→ 一行写入 CSV。

**分频值：** 15（对照）、12、11、10、9、8。**不要用 7**（214 MHz，超过 200 MHz 签核）。

**预测与判据：** 对照 §0.2 的「忙等等待」列。

| 实测 wait 对预测 | 含义 | 下一步 |
|---|---|---|
| 各档在 ±3% 内，且随 1/f 连续变化 | 时钟确实跟着寄存器走，平台是量化假象 | 拟合 `latency_model.py fit`（现在输入的是 wait，预期周期 ≈171 800，常数项 ≈0），进入 X4 |
| 仍然出现平台 | 时钟确实被钳位，或存在别的限制 | 需要 W2 的计数器；此时 MMCM 嫌疑重新升高 |
| 某一档 max LSB ≠ 0 | 该频率下功能出错 | 回退，记录，不再向上 |

**同时用相同流程重做旧 bit 与 RC1 的同口径 A/B**（忙等，各 1 万张），把 27.41 倍替换成不含量化误差的数。

**这一步还有一个副产品：** 如果梯度在 136–187 MHz 上连续并逐比特一致，说明 RC1 在 MMCM **合规**区间内工作正常，100 MHz 的「规格外」问题可以通过换到 ≥133.3 MHz 解决，而不必重新实现 BD。

## 3. X2：PS 热路径与生产模式

### 3.1 先做两个修复（零风险）

1. **启动前清 IOC 并验证已清**：对 MM2S 与 S2MM 的状态寄存器写 1 清除 IOC，读回确认为 0，再启动。W1 已证明漏掉这一步会提前判完成。
2. **完成后确认**：S2MM 状态无错误位、已接收长度 = 96、IOC 置位，才读输出。

### 3.2 热路径改成 C（用 ctypes 调用的小共享库，或独立的 C 程序）

一次帧内只做：写 src → 清并验证 IOC → 写 S2MM（目标地址、长度 96）→ 写 MM2S（源地址、长度 6144）→ 忙等 S2MM IOC → 读 96 B → 解码 → 稠密层 → 返回类别与原始 GAP。验证与记账放在帧循环之外：把每帧的 96 B 原始输出存进内存数组，批结束后统一与黄金 GAP 比较。

各项目标（由 §0.3 的实测值外推，均为 [假设]，用分项计时验证）：

| 项 | 现值 (ms) | 目标 | 手段 |
|---|---:|---|---|
| decode | 0.279 | ≤0.01 | 96 B 直接按 int32 视图读取，按固定缩放 |
| dense | 0.111 | ≤0.01 | 预先转好的权重、预分配输出；**用与现在相同的精度**，保证 Top-1 逐样本一致 |
| src | 0.151 | ≤0.03 | 在 C 里用宽位宽拷贝写入映射；或评估写合并映射/可缓存缓冲 + 显式同步 |
| start | 0.149 | ≤0.02 | C 里的寄存器写，约 8 次 |
| read | 0.075 | ≤0.01 | C 里读 12 个 64 位字 |

**哨兵保留：** 每帧预填 0xAA 并检查（C 里约 1 µs），检出事件就按 §4 的协议重读，不静默通过。

## 4. X3：0xAA 收尾（现在有了可检验的假设）

**假设 HX：** 历史事件是「读取发生在输出写入途中」，原因是完成判定早于最后一个突发落到内存（或线束提前判完成）。

**检验（对 RC1，100 MHz，不改硬件）：**

1. **IOC → 数据可见延迟分布。** 检测到 IOC 后立刻对输出的最后 8 字节（字节 88–95）做忙读，记录它首次不等于 0xAA 的时刻相对 IOC 检测的偏移；每帧一个值，记录 ≥10 万帧。读到正值的尾部（IOC 先于数据）就是事件的机理；若最大偏移 >0，则读取前需要的保护时间就有了定量依据。
2. **读两次**：IOC 后立即读一次，再读一次（间隔约 10 µs），任何不同都记为事件。soak 里每帧都做，生产模式按抽样。
3. 事件捕获协议沿用 v7 §3.1（重读三次、DMA 状态与长度、前三帧、帧序号、模式）。

**修复候选（在 1 有结论后）：** 完成后校验最后一个 64 位字不是哨兵值，不是就短暂重读；或者在读之前插入屏障并校验 S2MM 长度。

**收尾标准（二选一）：** 复现并修复；或在生产配置下累计 ≥380 万帧零事件（上界 <1/百万帧）。按生产路径改成 C 之后约 1.8 ms/帧，380 万帧约 1.9 小时，可以放在过夜任务里；分别对 100 MHz 与最终选定的时钟各做一遍。

## 5. X4：时钟决策

只有 X1 完成后才决定。

| X1 的结果 | 决策 |
|---|---|
| 连续缩放且 136–187 MHz 逐比特一致 | 候选工作点在 [133.3, 200] MHz 内（MMCM 合规、已签核），倾向 149.9 MHz（VCO 900 MHz，居中）。要求：X3 收尾 + 在该频率上的 30 分钟/380 万帧 soak + 多种子 WNS（5 ns 约束）。**这种情况下 W2 的 BD 重整不再紧迫** |
| 仍有平台 | 做 W2（去掉/重配 MMCM + 计数器），再重新梯度 |
| 梯度某档功能出错 | 工作点停在上一档，W5 的条件不变 |

**关于运行时写寄存器：** 更正 v7 的措辞。腐蚀只发生在「加载状态下写寄存器」。「先写寄存器、再重新加载」会让 fabric 在新时钟下从干净状态开始，所以这个**顺序本身是可用的启动流程**，前提是：自动化在会话启动脚本里、读回确认、KAT 通过、**不允许在 fabric 已加载并运行时再写**。W5 的前置条件里「必须由 overlay 在加载前设置」可以放宽为这个顺序；overlay 仍然是更干净的做法，但不是门。
